# V1 scope — The Commons

This is the checklist for the Grok preview client, after Brandon says
**BUILD**. Nothing here authorizes writing that client this session.

## In scope

- All **12 outdoor regions**, continuous, uniform 24×20 tiles, lightly
  dressed per `atlas.md`.
- **One demo house interior** (16×16): table, two chairs, wall slot (empty
  frame — no glue), rug. This is the only interior instance actually
  reachable in V1; the schema supports many, V1 needs one.
- **Lab interior** (20×16): three lookup stations (see `pushback.md` for the
  rewritten third recipe), each producing a placeable/wall-able item.
- **Homestead Row:** 1 functional demo-house door + up to 6 dynamic doors,
  all 6 rendering **boarded** in V1 (no friends glue to resolve them — see
  `glue.md`). This is correct V1 behavior, not a stub to apologize for.
- **Hall Lawn door** → `https://liquidgov.us/proposals`, new tab, one-line
  confirm. Works with zero glue.
- **Quarry Ridge boarded mine** — decorative dead end, sign, sit-rock.
- **Guest identity:** pick a throwaway display name at start. No login, no
  cookie check.
- **Presence:** per-region ~2 Hz broadcast (`presence.md`), RAM only.
- **Controls:** on-screen d-pad (touch) + arrows/WASD (keyboard), A/D =
  left/right, one interact prompt at doors/set pieces.
- **Camera:** 240×160 landscape / 3× desktop, 160×240 portrait / 2× phone
  (`art.md`).

## V1 inventory is session-scoped, not SQLite

There is no bound player identity pre-glue, so there is nothing durable to
write. V1's lab-output pickups live with presence in RAM for the session
and vanish on disconnect, same as a guest's position does. `schema.sql`'s
`inventory`/`placed` tables model the real future shape (a bound player
picking something up and placing it in their actual house) — V1 does not
need to hit them, and Grok's preview should not invent a fake persistence
layer to make guests' pickups "feel" durable. If it disappears when a guest
refreshes the tab, that's correct, not a bug.

## Out of scope

- Real per-player house instances, real persistence of anything (post-glue).
- Real friends-query resolution of Homestead's 6 dynamic doors (post-glue).
- Trading, crafting loop, farming, swimming.
- Workshop interior (shutter stays closed), Mine interior (adit stays
  boarded), Hall interior (door stays the whole interaction).
- XP, quest log, combat, day/night, weather, required soundtrack, character
  creator, isometric or 3D rendering.
- Photo capture / civic blob+feed — not even a fake button in V1 (see
  `glue.md`; this is genuinely not-yet-built, not a V1 stub).
- Any civic UI clone, any edit under `liquidgov-platform/`, any new LGP1
  tag, any write to `liquidgov_http`.
- Wiring `schema.sql` into the preview client for real. The schema exists so
  the *next* build (droplet sibling, post-BUILD-of-BUILD) doesn't invent a
  different shape — V1's preview may seed/mock it in memory if useful, but
  standing it up as a real SQLite file is not required to ship V1.

## Definition of done for V1

A guest can: name themselves, walk all 12 regions continuously, see another
concurrent guest moving at ~2 Hz, open the demo house and see the wall
slot's empty frame, visit the lab and trigger all three lookups, see
Homestead's 6 doors boarded and the demo door working, open the Hall door
to `/proposals`, and see Quarry Ridge's boarded mine — on both a desktop
browser and a phone in portrait, using either keyboard or the on-screen
d-pad. Nothing above requires touching `liquidgov_http`.
